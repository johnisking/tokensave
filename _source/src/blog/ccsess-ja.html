Claude Code で作業していると、長い会話をそのまま続けるか、新しい会話を始めるかで迷うことがあります。会話が長くなるほど毎回それまでの内容を送り直すので、新しく始めたほうが安そうにも見えます。逆に、新しい会話はプロジェクトを最初から把握し直すので、かえって高くつきそうにも思えます。途中で /compact を使えば費用は減るのか、昼休みから戻ったときの最初のメッセージがなぜ重いのか、という疑問もよく見かけます。

ネットには「会話が長いとトークンの無駄」「/clear をこまめに」「/compact を使おう」といったアドバイスがたくさんあります。ただ、同じ作業をやり方だけ変えて、実際の費用を比べた数字はなかなか見つかりません。そこで、同じゲームに同じ修正依頼30件を3つのやり方で送って費用を測り、さらに休憩時間を0分から65分まで変えて、次のメッセージの費用がどう変わるかも測りました。

測定日は2026年10月20日、Claude Code 2.1.295 と Claude Opus 5.5 を使いました。サブスクのプランでログインした状態で、費用は Claude Code が結果と一緒に返す API 定価換算の金額（total_cost_usd）です。金額は1ドル＝158円で換算し、円を先に、ドルを括弧に書いています。

どうやって測ったか

2つの実験をしました。共通の設定は次のとおりです。

項目 設定
ツール Claude Code 2.1.295、ヘッドレスモード（-p）
モデル Claude Opus 5.5、effort は medium
ログイン サブスクのプラン
MCP サーバー なし
測定日 2026年10月20日、各やり方2回

実験1（長い会話と新しい会話）: 最初の依頼でブラウザで動くブロック崩しゲームを作らせ、続けてボールの色、レベルの追加、効果音、タッチ操作、最後のコード整理まで、修正依頼を29件送りました。同じ30件の依頼を3つのやり方で送っています。

  • 1つのセッション: 30件すべてを同じ会話で続けて送る
  • 1つのセッション＋/compact: 同じやり方で、15件目のあとに /compact で会話を要約する
  • 毎回新しいセッション: 依頼ごとに新しい会話を開き、「ゲームは現在のフォルダの index.html にある」という一文を先頭に付ける

実験2（休憩時間）: 同じブロック崩しゲームを作らせたあと、0分、4分、6分、15分、30分、55分、65分待ってから、同じ会話で「ボールを赤く、少し速く」と頼みました。待ったあとに送ったこの2つ目のメッセージの費用を比べています。

依頼30件の中身

修正依頼は、実際にゲームを仕上げるときに出しそうな小さな依頼を選びました。ほとんどが同じファイル（index.html）1つを直す依頼で、後半になるほどゲームのコードは大きくなります。30件目の依頼が終わった時点で、ゲームのファイルは約30〜40KBでした。

依頼番号 内容の例
1 ブロック崩しゲームを作る（レベル2つ、スコア、残機3、キーボード・マウス）
2〜8 ボールの色、パドルの幅、スタート画面、レベル表示、ブロックの色、一時停止、ボールの速さ
9〜15 3つ目のレベル、クリア画面、ハイスコアの保存、2回で壊れるブロック、効果音、ミュート、ウィンドウサイズへの対応
16〜22 壊れるときの演出、ボーナスの残機、アイテム、ハートでの残機表示、発射の仕方、タッチ操作、背景
23〜30 レベルごとのタイム、リスタートボタン、パドルの減速、コンボ、操作の説明、ピラミッド型の配置、難易度の選択、コードの整理

依頼ごとにかかった時間を合計すると、3つのやり方とも約19分でした。時間はほぼ同じで、差が出たのは費用だけです。

実験1：同じ依頼30件、3つのやり方

3つのやり方をそれぞれ2回ずつ実行した結果です。6回とも、30件目の依頼のあとにゲームは正常に動きました。

やり方 合計費用（1回目・2回目） 平均 1つのセッションとの差
1つのセッション $4.05・$4.27 約657円（$4.16） 基準
1つのセッション＋/compact $4.42・$4.99 約743円（$4.70） +13%
毎回新しいセッション $9.19・$9.84 約1,504円（$9.52） +129%

毎回新しいセッションを開いたやり方が、いちばん高くなりました。 1つのセッションで続けた場合より129％多くかかり、2回の実行で同じ傾向でした。/compact を1回使ったやり方も、かえって13％高くなっています。

依頼1件あたりの費用を、前半と後半に分けて見ると違いがよく分かります。

やり方 依頼2〜5（1件平均） 依頼26〜30（1件平均）
1つのセッション 約4.6円（$0.029） 約44.9円（$0.284）
1つのセッション＋/compact 約5.5円（$0.035） 約42.8円（$0.271）
毎回新しいセッション 約33.2円（$0.210） 約68.7円（$0.435）

長い会話ほど1件あたりが高くなるのは本当です。1つのセッションでは、後半の依頼は前半より約870％高くなりました。依頼のたびに長くなった会話全体を読み直し、ゲームのコード自体も大きくなり続けたからです。それでも同じ時点の新しいセッション（$0.435）よりは安く、前半の依頼は新しいセッションより86％安く済みました。

新しい会話はなぜ高かったのか

面白いのは入力トークンの合計です。毎回新しいセッションのやり方は、30件で入力トークンが約508万と、1つのセッション（約663万）よりむしろ少なくなりました。それなのに費用は129％多くかかっています。差はトークンの量ではなく、種類から生まれていました。

Claude Code は、システムプロンプト、ツールの説明、それまでの会話をプロンプトキャッシュに保存し、次の依頼でその部分を安く読み直します。Opus 5.5 の料金は次のように分かれています。

トークンの種類 100万トークンあたり 通常の入力との差
通常の入力 $4 基準
キャッシュ書き込み（1時間） $8 +100%
キャッシュ読み込み $0.20 -95%
出力 $20 +400%

1つのセッションでは、ほとんどのトークンがいちばん安い「キャッシュ読み込み」でした。一方、新しいセッションは会話がないので、毎回ゲームのファイルを開き直し、その内容をいちばん高い「キャッシュ書き込み」で新しく保存する必要がありました。測ってみると、依頼1件あたりに新しくキャッシュに書いたトークンは、1つのセッションが平均4,061、新しいセッションが29,178でした。モデルを呼び出した回数も、依頼1件あたり5.2回と6.7回で新しいセッションのほうが多くなっています。プロジェクトを把握し直すコストが、毎回上乗せされていたわけです。

どうしても新しいセッションを開くなら

別の作業に移るときのように、新しいセッションを開くのが正しい場面もたくさんあります。今回、新しいセッションが高くついた理由は「プロジェクトを把握し直すコスト」だったので、そのコストを減らせばよいわけです。

  • ファイルの場所をすぐに伝える。 今回の実験でも「ゲームは index.html にある」という一文を付けました。どのファイルを直すかを伝えれば、フォルダを探し回る手順が減ります。
  • CLAUDE.md にプロジェクトの要約を短く書いておく。 構成と主なファイルを数行で書いておけば、新しいセッションが毎回同じ探索をくり返さずに済みます。ただし CLAUDE.md はリクエストのたびに一緒に送られるので、長く書くと逆に損をします。トークンセーブの実測では、1KB でリクエストごとに約320トークンでした（CLAUDE.md のサイズの実測）。
  • 1つのセッションでやることはまとめて頼む。 同じファイルを何度も直す予定なら、依頼を1件ずつ新しいセッションで送るより、1つのセッションの中で続けて送るほうがキャッシュを活かし続けられます。

/compact で費用は減るのか

今回の測定では減りませんでした。15件目の依頼のあとに /compact を実行すると、要約そのものに毎回$0.11（約17.4円）かかりました。要約はそれまでの会話をすべて読み、新しく書き直す作業なので、大きな依頼1件と同じです。さらに、要約された会話はキャッシュに保存された元の会話と中身が変わるため、次の依頼でキャッシュを積み直す必要がありました。

要約のおかげで後半の依頼は少し安くなりました（26〜30件目の平均 $0.284 → $0.271）。しかし残り15件で節約できた額が、要約の費用とキャッシュを積み直す費用を取り戻せず、全体では13％高くなりました。

Claude Code の公式ドキュメントも、/compact は会話を要約する大きなリクエストだと説明しています。/compact が役に立つのは、次のような場面です。

  • 会話がコンテキストの上限に近いとき: 上限に達すればどのみち自動で要約されます。自分のタイミングで要約すれば、残す内容を指定できます。
  • 会話がこじれてモデルが混乱しているとき: 試行錯誤が長く残っていると、回答がぼやけることがあります。
  • 長い休憩の直前: 公式ブログは、キャッシュが生きているうちに要約するほうが、休憩後に要約するより安いと案内しています。ただし、今回の測定ではこのケースは測っていません。

実験2：休憩時間とキャッシュの1時間

2つ目の実験は休憩時間です。ゲームを作らせたあと一定時間待ってから小さな修正を頼み、そのメッセージの最初のモデル呼び出しでキャッシュをどれだけ読み、どれだけ書いたかを見ました。2回測った平均です。

休憩時間 キャッシュから読み込み キャッシュに新しく書き込み 次のメッセージの費用 キャッシュ
0分 41,436 496 約6.2円（$0.039） 有効
4分 43,232 466 約6.6円（$0.042） 有効
6分 42,440 496 約6.6円（$0.042） 有効
15分 43,076 502 約6.5円（$0.041） 有効
30分 42,636 494 約6.8円（$0.043） 有効
55分 43,183 502 約6.8円（$0.043） 有効
65分 15,925 27,460 約40.0円（$0.253） 期限切れ

55分までは何も変わりませんでした。 0分休んでも55分休んでも、次のメッセージは約$0.042でした。65分休むとキャッシュの期限が切れて27,460トークンを書き直す必要があり、同じメッセージが$0.253と507％高くなりました。

今回の実行で Claude Code が使ったキャッシュは、すべて1時間のものでした（使用量の記録の ephemeral_1h）。Anthropic API の標準のキャッシュは5分ですが、サブスクで使う Claude Code は1時間のキャッシュを使います。そのため、5分のキャッシュなら逃していたはずの6分や15分の休憩でも、追加の費用はかかりませんでした。

今回のゲームは、会話の中身が約4万トークンの小さなプロジェクトでした。キャッシュが切れたときに書き直す量は、会話全体の大きさに比例します。実験1の長い会話は20万トークンを超えていたので、その規模の会話で1時間以上休むと、最初のメッセージにはずっと大きな費用がかかります。

会話が大きいと期限切れのコストはどれくらいか

今回の実験2の会話は約4万トークンだったので、キャッシュが切れても次のメッセージは$0.253（約40円）でした。会話がもっと大きい場合を Opus 5.5 の料金で計算すると、次のようになります。出力や新しく読むファイルは除き、会話全体をキャッシュに書き直す費用だけを計算した値です。

会話の大きさ キャッシュが有効なとき（読み込み） キャッシュが切れたとき（書き直し）
4万トークン 約1.3円（$0.008） 約51円（$0.32）
10万トークン 約3.2円（$0.02） 約126円（$0.80）
20万トークン 約6.3円（$0.04） 約253円（$1.60）

実験1の長い会話のように20万トークンを超えるセッションなら、1時間以上休んで戻った最初のメッセージ1件に、会話を書き直す費用だけで$1.60かかります。キャッシュ読み込みの4,000％の水準です。大きなセッションを長く空ける予定なら、この費用を考えておくとよいでしょう。

キャッシュが5分の場合もある

Claude Code の公式ドキュメントによると、キャッシュの有効時間はログイン方法によって変わります。

ログイン方法 キャッシュの有効時間
サブスク（Pro、Max など） 1時間
サブスクで使用量クレジットを使っている間 5分
API キー、クラウドプロバイダー 標準で5分

API キーで Claude Code を使っているなら、5分席を外しただけでキャッシュが切れることがあります。今回の6分や15分の休憩は、API キーの利用者にとってはどれも「期限切れ」側に入りうるということです。公式ドキュメントでは、環境変数でキャッシュの時間を自分で選ぶ方法も案内されています。

また、会話の途中でモデルや effort を変えると、キャッシュは使えなくなります。モデルを変えるなら、新しい作業を始めるときに変えるほうが安く済みます。

自分のセッションのキャッシュの状態を確かめる

Claude Code の公式ドキュメントによると、バージョン2.1.251から /usage の画面に「Prompt cache (main)」の行が表示されます。今のセッションで入力トークンの何％をキャッシュから読んだか、キャッシュを逃した回数（misses）、キャッシュが今も有効か（warm）と有効時間（1h TTL など）が分かります。/compact のように Claude Code 自身が会話を書き直した場合は「expected rebuild」として別に数えられます。

サブスクのプランなら、同じ画面で、長いコンテキストやキャッシュの取りこぼしが最近の使用量の10％以上を占めたときに別途表示されます。長い休憩から戻ったときに /usage を開いてキャッシュが cold になっていれば、次のメッセージで会話全体を書き直すことになると考えてください。

場面別のおすすめ

2つの実験の結果をまとめると、次のようになります。

場面 おすすめ 理由
同じプロジェクトを続けて直すとき 1つのセッションで続ける キャッシュ読み込みが最も安く、新しいセッションは129％高かった
関係のない新しい作業に移るとき /clear または新しいセッション 不要な会話を読み続ける必要がない
会話が上限に近い、またはこじれたとき /compact 節約にはならないが、整理の効果がある
1時間以内の休憩 そのまま続ける 55分まで費用は変わらなかった
1時間以上休んで戻るとき 会話が大きければ、必要な内容だけ持って新しく始めることも検討 期限切れのキャッシュを会話全体ぶん書き直すことになる

ポイントは「会話が長いから高い」よりも、「キャッシュを積み直す瞬間が高い」ということです。新しいセッション、/compact、1時間を超える休憩は、どれもキャッシュの積み直しを引き起こします。同じ作業を続けている間は、そうした瞬間を減らすほうが安く済みます。

サブスクの場合

Pro や Max のプランはトークン単位で料金を払わないので、この記事の金額がそのまま請求されるわけではありません。ただし使用量の上限は使ったトークンに応じて減り、キャッシュ書き込みのような高いトークンほど上限を多く消費します。毎回新しいセッションを開く習慣は、同じ作業で上限を早く使い切ることにつながります。

自分が実際にどのセッションでどれだけ使ったかは、使用量アナライザーに ~/.claude/projects フォルダを入れると、日付やプロジェクト別に確認できます。1日の作業量からサブスクと API のどちらが得かは、エージェント費用計算機で比べられます。上限の減り方は Claude の使用量上限まとめ にまとめています。

今回の依頼30件の一覧、依頼ごとのトークンと費用、元の記録は、長い会話と新しい会話の実測データと休憩時間とキャッシュの実測データからダウンロードできます。

今回の測定の限界

  • プロジェクトは1つ: 30〜40KB のゲームファイル1つを直す作業でした。複数のファイルを行き来したり、関係のない作業が混ざったりする長いセッションでは、結果が変わる可能性があります。
  • 同じ時間帯に実行: 3つのやり方（実験2では7通りの休憩）を同じ時間帯に並べて実行しました。そのため、共通のシステムプロンプトの一部がほかのセッションのおかげでキャッシュに残っていた可能性があります。65分の休憩でも15,925トークンはキャッシュから読まれていました。セッションを1つだけ動かす場合、期限切れのコストはもう少し大きくなるかもしれません。
  • Opus 5.5 と Claude Code のみ: ほかのモデルや Codex のような別のツールはキャッシュの仕組みが違うので、数字も変わります。Codex も一緒に実行しましたが、いくつも同時に動かすとファイルの書き込みで止まってしまったため、結果から外しました。
  • 費用は API 定価での換算: サブスクではこの金額は請求されず、同じ割合で使用量の上限が減ります。

よくある質問

Claude Code で新しい会話をこまめに開くとトークンの節約になりますか？ 同じプロジェクトを直し続けている間は、なりません。今回の測定では、依頼ごとに新しいセッションを開いたやり方が、1つのセッションで続けた場合より129％高くなりました。新しいセッションはプロジェクトを把握し直すために、高いキャッシュ書き込みを毎回していました。

/compact を使うと費用は減りますか？ 今回の測定では13％増えました。要約そのものが大きなリクエストで、要約のあとはキャッシュを積み直す必要があるからです。会話が上限に近いときやこじれたときの整理用と考えるのがよさそうです。

Claude Code のキャッシュは何分もちますか？ サブスクでログインしていれば1時間です。今回の測定でも55分まではキャッシュが有効で、65分では切れていました。API キーで使っている場合や、使用量クレジットを使っている間は標準で5分です。

/clear と新しいセッションは違いますか？ どちらも会話を空にして始め直す点は同じです。公式ドキュメントは、関係のない作業に移るときに /clear を使い、あとで戻りたいセッションは /rename で名前を付けておくよう案内しています。

昼休みの前に /compact をすれば節約できますか？ 公式ブログは、キャッシュが有効なうちに要約するほうが、休憩のあとで要約するより安いと案内しています。要約された会話は元の会話より小さいので、戻ってから書き直す量も減ります。ただし、今回の測定ではこのケースを直接は測っていません。

会話が長くなったら、いずれは新しく始めたほうがいいのでは？ 今回の30件では、最後まで1つのセッションのほうが安く済みました。ただし、プロジェクトと関係のない内容がたまったとき、1時間以上休んでキャッシュが切れたとき、コンテキストの上限に近いときは、新しく始めたほうがよい場合があります。

まとめ

同じゲームに同じ修正依頼30件を送ったところ、1つのセッションで続けたやり方がいちばん安く済みました（平均$4.16）。15件目のあとに /compact を使ったやり方は13％、依頼ごとに新しいセッションを開いたやり方は129％高くなりました。新しいセッションは入力トークンがむしろ少なかったものの、毎回プロジェクトを読み直し、高いキャッシュ書き込みをする必要がありました。

休憩時間の実験では、55分までは次のメッセージの費用がまったく同じで、65分休むとキャッシュが切れて507％高くなりました。同じ作業は1つのセッションで続け、新しいセッションは別の作業に移るときに、/compact は整理が必要なときに使う。これが今回の測定から見えた、いちばん安い使い方です。プロジェクト1つ、やり方ごとに2回の測定なので、プロジェクトの大きさや依頼の内容によって数字は変わる可能性があります。
