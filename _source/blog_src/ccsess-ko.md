![클로드 코드 긴 대화 vs 새 대화: 비용 실측](/claude-code-gin-daehwa-biyong-ko.jpg)

클로드 코드로 작업하다 보면 긴 대화를 계속 이어 갈지, 새 대화를 열지 고민하게 됩니다. 대화가 길어질수록 매번 앞의 내용을 다시 보내니 새로 여는 편이 쌀 것 같기도 하고, 반대로 새 대화는 프로젝트를 처음부터 다시 파악해야 하니 더 비쌀 것 같기도 합니다. 중간에 /compact로 대화를 요약하면 돈이 줄어드는지, 점심을 먹고 돌아왔을 때 첫 메시지가 왜 유독 무거운지도 자주 나오는 질문입니다.

인터넷에는 "대화가 길면 토큰 낭비", "/clear를 자주 하라", "/compact를 쓰라" 같은 조언이 많지만, 같은 작업을 방법만 바꿔 실제로 비용을 비교한 숫자는 찾기 어렵습니다. 그래서 같은 게임에 같은 수정 요청 30개를 세 가지 방법으로 보내 비용을 쟀고, 쉬는 시간을 0분부터 65분까지 바꿔 가며 다음 메시지 비용이 어떻게 달라지는지도 쟀습니다.

측정은 2026년 10월 20일에 Claude Code 2.1.295와 Claude Opus 5.5로 했습니다. 구독 요금제로 로그인한 상태였고, 비용은 Claude Code가 결과와 함께 돌려주는 API 정가 환산 금액(total_cost_usd)입니다. 이 글의 원화는 1달러=1,340원으로 계산했습니다.

**실험 1 (긴 대화 vs 새 대화):** 첫 요청으로 브라우저에서 돌아가는 벽돌깨기 게임을 만들게 하고, 이어서 공 색깔, 레벨 추가, 효과음, 터치 조작, 마지막 코드 정리까지 수정 요청 29개를 더 보냈습니다. 같은 30개 요청을 세 가지 방법으로 보냈습니다.

- **한 세션:** 30개를 모두 같은 대화에서 이어서 보냄
- **한 세션 + /compact:** 같은 방법이지만 15번째 요청 뒤에 /compact로 대화를 요약
- **매번 새 세션:** 요청마다 새 대화를 열고 "게임은 현재 폴더의 index.html에 있다"는 한 문장을 앞에 붙임

**실험 2 (쉬는 시간):** 같은 벽돌깨기 게임을 만들게 한 뒤, 0분, 4분, 6분, 15분, 30분, 55분, 65분을 기다렸다가 같은 대화에서 "공을 빨간색으로, 조금 더 빠르게" 바꿔 달라고 했습니다. 기다린 뒤 보낸 이 두 번째 메시지의 비용을 비교했습니다.

## 요청 30개는 이런 것이었다

수정 요청은 실제로 게임을 다듬을 때 할 법한 작은 요청들로 골랐습니다. 대부분 같은 파일(index.html) 하나를 고치는 요청이고, 뒤로 갈수록 게임 코드가 커집니다. 30번째 요청이 끝났을 때 게임 파일은 약 30~40KB였습니다.

| 요청 번호 | 내용 예시 |
|---|---|
| 1 | 벽돌깨기 게임 만들기 (레벨 2개, 점수, 목숨 3개, 키보드·마우스) |
| 2~8 | 공 색깔, 패들 너비, 시작 화면, 레벨 표시, 벽돌 색, 일시정지, 공 속도 |
| 9~15 | 세 번째 레벨, 승리 화면, 최고 점수 저장, 두 번 깨지는 벽돌, 효과음, 음소거, 창 크기 맞춤 |
| 16~22 | 깨질 때 효과, 보너스 목숨, 아이템, 하트 목숨 표시, 발사 방식, 터치 조작, 배경 |
| 23~30 | 레벨별 시간, 재시작 버튼, 패들 감속, 콤보, 조작 안내, 피라미드 배치, 난이도 선택, 코드 정리 |

요청마다 걸린 시간을 합치면 세 방법 모두 약 19분이었습니다. 시간은 거의 같았고, 차이는 비용에서만 났습니다.

## 실험 1: 같은 요청 30개, 세 가지 방법

## 새 대화가 왜 더 비쌌을까

흥미로운 점은 입력 토큰 총량입니다. 매번 새 세션은 30개 요청 동안 입력 토큰이 약 508만으로, 한 세션(약 663만)보다 오히려 적었습니다. 그런데도 비용은 129% 더 나왔습니다. 차이는 토큰의 양이 아니라 종류에서 생겼습니다.

Claude Code는 시스템 프롬프트, 도구 설명, 지금까지의 대화를 프롬프트 캐시에 저장해 두고, 다음 요청에서 그 부분을 싸게 다시 읽습니다. Opus 5.5의 가격은 이렇게 나뉩니다.

| 토큰 종류 | 100만 토큰당 가격 | 일반 입력 대비 |
|---|---:|---:|
| 일반 입력 | $4 | 기준 |
| 캐시 쓰기 (1시간) | $8 | +100% |
| 캐시 읽기 | $0.20 | -95% |
| 출력 | $20 | +400% |

한 세션에서는 대부분의 토큰이 가장 싼 "캐시 읽기"였습니다. 반면 새 세션은 대화가 없으니 매번 게임 파일을 다시 열어 보고, 그 내용을 가장 비싼 "캐시 쓰기"로 새로 저장해야 했습니다. 측정해 보니 요청 하나당 새로 캐시에 쓴 토큰이 한 세션은 평균 4,061개, 새 세션은 29,178개였습니다. 모델을 부른 횟수도 요청당 5.2번 대 6.7번으로 새 세션이 더 많았습니다. 새 세션은 먼저 폴더와 파일을 살펴보는 단계를 거친 뒤에야 실제 수정을 시작했기 때문입니다. 프로젝트를 다시 파악하는 데 드는 비용이 매번 붙은 셈입니다.

## 새 세션을 꼭 열어야 한다면

다른 작업으로 넘어갈 때처럼 새 세션을 여는 게 맞는 경우도 많습니다. 이번 측정에서 새 세션이 비쌌던 이유가 "프로젝트를 다시 파악하는 비용"이었으니, 그 비용을 줄이면 됩니다.

- **파일 위치를 바로 알려 주세요.** 이번 실험에서도 "게임은 index.html에 있다"는 한 문장을 붙였습니다. 어떤 파일을 고칠지 알려 주면 폴더를 뒤지는 단계가 줄어듭니다.
- **CLAUDE.md에 프로젝트 요약을 짧게 적어 두세요.** 구조와 주요 파일을 몇 줄로 적어 두면 새 세션이 매번 같은 탐색을 반복하지 않아도 됩니다. 다만 CLAUDE.md는 요청마다 함께 보내지므로 길게 쓰면 오히려 손해입니다. 토큰세이브 실측에서는 1KB가 요청마다 약 320토큰이었습니다([CLAUDE.md 크기 실측](/data/claude-md-agents-md-size)).
- **한 세션에서 할 일은 묶어서 하세요.** 같은 파일을 여러 번 고칠 계획이라면 요청을 하나씩 새 세션으로 보내기보다, 한 세션 안에서 이어서 보내는 편이 캐시를 계속 활용할 수 있습니다.

## /compact는 돈을 아껴 줄까

![/compact는 돈을 아껴 줄까: 대화가 컨텍스트 한도에 가까울 때; 대화가 꼬여서 모델이 헷갈릴 때; 오래 쉬기 직전](/claude-code-gin-daehwa-biyong-compact-ko.jpg)

이번 측정에서는 아끼지 못했습니다. 15번째 요청 뒤에 /compact를 실행하니, 요약 작업 자체에 $0.11씩 들었습니다. 요약은 지금까지의 대화를 전부 읽고 새로 쓰는 작업이라 큰 요청 하나와 같습니다. 그리고 요약된 대화는 캐시에 저장된 원래 대화와 내용이 달라져서, 다음 요청에서 캐시를 다시 쌓아야 했습니다.

요약 덕분에 뒤쪽 요청이 조금 싸지기는 했습니다(26~30번 요청 평균 $0.284 → $0.271). 하지만 남은 15개 요청 동안 아낀 금액이 요약 비용과 캐시를 다시 쌓는 비용을 메우지 못해서, 전체로는 13% 더 들었습니다.

Claude Code 공식 문서도 /compact는 대화를 요약하는 큰 요청이라고 설명합니다. /compact가 쓸모 있는 때는 따로 있습니다.

- **대화가 컨텍스트 한도에 가까울 때:** 한도에 닿으면 어차피 자동으로 요약됩니다. 원하는 시점에 직접 요약하면 남길 내용을 지정할 수 있습니다.
- **대화가 꼬여서 모델이 헷갈릴 때:** 시행착오가 길게 남아 있으면 답이 흐려지기도 합니다.
- **오래 쉬기 직전:** 공식 블로그는 캐시가 살아 있을 때 요약하는 편이 쉬고 나서 요약하는 것보다 싸다고 안내합니다. 다만 이번 측정에서 이 경우는 재지 않았습니다.

## 실험 2: 쉬는 시간과 캐시 1시간

두 번째 실험은 쉬는 시간입니다. 캐시가 몇 분 동안 살아 있는지는 로그인 방식과 버전에 따라 다를 수 있어서, 문서만 보지 않고 실제로 기다려 보며 확인했습니다. 5분 캐시라면 4분과 6분 사이에서, 1시간 캐시라면 55분과 65분 사이에서 비용이 갑자기 뛰어야 합니다. 게임을 만든 뒤 일정 시간을 기다렸다가 작은 수정을 요청했고, 그 메시지의 첫 모델 호출에서 캐시를 얼마나 읽고 썼는지를 봤습니다. 두 번 잰 평균입니다.

| 쉬는 시간 | 캐시에서 읽음 | 캐시에 새로 씀 | 다음 메시지 비용 | 캐시 |
|---|---:|---:|---:|---|
| 0분 | 41,436 | 496 | $0.039 (약 52원) | 유지 |
| 4분 | 43,232 | 466 | $0.042 (약 56원) | 유지 |
| 6분 | 42,440 | 496 | $0.042 (약 56원) | 유지 |
| 15분 | 43,076 | 502 | $0.041 (약 55원) | 유지 |
| 30분 | 42,636 | 494 | $0.043 (약 58원) | 유지 |
| 55분 | 43,183 | 502 | $0.043 (약 58원) | 유지 |
| 65분 | 15,925 | 27,460 | **$0.253 (약 339원)** | 만료 |

**55분까지는 아무것도 달라지지 않았습니다.** 0분을 쉬든 55분을 쉬든 다음 메시지는 약 $0.042였습니다. 65분을 쉬자 캐시가 만료돼 27,460토큰을 다시 써야 했고, 같은 메시지가 $0.253으로 507% 비싸졌습니다.

이번 실행에서 Claude Code가 쓴 캐시는 모두 1시간짜리였습니다(사용량 기록의 ephemeral_1h). Anthropic API의 기본 캐시는 5분인데, 구독 요금제로 쓰는 Claude Code는 1시간 캐시를 씁니다. 그래서 5분 캐시라면 놓쳤을 6분, 15분 휴식도 추가 비용이 없었습니다.

이번 게임은 대화 내용이 약 4만 토큰인 작은 프로젝트였습니다. 캐시가 만료됐을 때 다시 써야 하는 양은 대화 전체 크기에 비례합니다. 실험 1의 긴 대화는 20만 토큰을 넘었으니, 그 정도 대화에서 1시간 넘게 쉬면 첫 메시지에 훨씬 큰 비용이 붙습니다.

## 대화가 크면 만료 비용은 얼마나 될까

이번 실험 2의 대화는 약 4만 토큰이라 캐시가 만료돼도 다음 메시지가 $0.253(약 339원)이었습니다. 대화가 더 크면 얼마나 될지 Opus 5.5 가격으로 계산해 보면 이렇습니다. 출력과 새로 읽는 파일은 빼고, 대화 전체를 캐시에 다시 쓰는 비용만 계산한 값입니다.

| 대화 크기 | 캐시가 살아 있을 때 (읽기) | 캐시가 만료됐을 때 (다시 쓰기) |
|---|---:|---:|
| 4만 토큰 | $0.008 (약 11원) | $0.32 (약 429원) |
| 10만 토큰 | $0.02 (약 27원) | $0.80 (약 1,072원) |
| 20만 토큰 | $0.04 (약 54원) | $1.60 (약 2,144원) |

실험 1의 긴 대화처럼 20만 토큰이 넘는 세션이라면, 1시간 넘게 쉬고 돌아온 첫 메시지 하나에 대화를 다시 쓰는 비용만 $1.60이 붙습니다. 캐시 읽기의 4,000% 수준입니다. 큰 세션을 오래 비워 둘 예정이라면 이 비용을 감안하는 것이 좋습니다. 반대로 대화가 작은 세션이라면 만료돼도 몇백 원 수준이라 크게 신경 쓸 필요는 없습니다.

## 캐시가 5분인 경우도 있다

Claude Code 공식 문서에 따르면 캐시 유지 시간은 로그인 방식에 따라 다릅니다.

| 로그인 방식 | 캐시 유지 시간 |
|---|---|
| 구독 요금제 (Pro, Max 등) | 1시간 |
| 구독 + 사용 크레딧으로 쓰는 중 | 5분 |
| API 키, 클라우드 제공사 | 기본 5분 |

API 키로 Claude Code를 쓴다면 5분만 자리를 비워도 캐시가 만료될 수 있습니다. 이번 실험의 6분, 15분 휴식이 API 키 사용자에게는 모두 "만료" 쪽에 들어갈 수 있다는 뜻입니다. 공식 문서는 환경 변수로 캐시 시간을 직접 고르는 방법도 안내합니다.

또 캐시는 모델이나 effort를 대화 중간에 바꾸면 깨집니다. 모델을 바꿔야 한다면 새 작업을 시작할 때 바꾸는 편이 쌉니다.

## 내 세션의 캐시 상태 확인하기

Claude Code 공식 문서에 따르면 2.1.251 버전부터 /usage 화면에 "Prompt cache (main)" 줄이 표시됩니다. 지금 세션에서 입력 토큰 중 몇 %를 캐시에서 읽었는지, 캐시를 놓친 횟수(misses), 지금 캐시가 살아 있는지(warm)와 유지 시간(1h TTL 등)을 보여 줍니다. /compact처럼 Claude Code가 직접 대화를 고쳐 쓴 경우는 "expected rebuild"로 따로 셉니다.

구독 요금제라면 같은 화면에서 최근 사용량 중 긴 컨텍스트나 캐시 놓침이 10% 이상을 차지할 때 따로 표시해 줍니다. 오래 쉬었다 돌아왔을 때 /usage를 한 번 열어 캐시가 cold로 나오면, 다음 메시지는 대화 전체를 다시 쓰게 된다고 보면 됩니다.

## 상황별로 어떻게 쓰면 좋을까

두 실험 결과를 정리하면 이렇습니다.

| 상황 | 추천 | 이유 |
|---|---|---|
| 같은 프로젝트를 계속 고칠 때 | 한 세션으로 이어 가기 | 캐시 읽기가 가장 싸고, 새 세션은 129% 더 들었음 |
| 관련 없는 새 작업으로 넘어갈 때 | /clear 또는 새 세션 | 쓸모없는 대화를 계속 읽을 필요가 없음 |
| 대화가 한도에 가깝거나 꼬였을 때 | /compact | 비용 절약용은 아니지만 정리 효과가 있음 |
| 1시간 안쪽 휴식 | 그대로 이어 가기 | 55분까지 비용 변화 없음 |
| 1시간 넘게 쉬었다 올 때 | 대화가 크면 필요한 내용만 들고 새로 시작 검토 | 만료된 캐시를 대화 전체만큼 다시 써야 함 |

표에서 보듯 비용을 가장 크게 바꾼 건 대화의 길이가 아니라 캐시였습니다. 핵심은 "대화가 길어서 비싸다"보다 "캐시를 다시 쌓는 순간이 비싸다"는 점입니다. 새 세션, /compact, 1시간 넘는 휴식은 모두 캐시를 다시 쌓게 만듭니다. 같은 작업을 이어 가는 동안에는 그런 순간을 줄이는 쪽이 쌉니다.

## 구독 요금제라면

Pro나 Max 요금제는 토큰 단위로 돈을 내지 않으니, 이 글의 금액이 그대로 청구되지는 않습니다. 하지만 사용 한도는 쓴 토큰만큼 줄어들고, 캐시 쓰기처럼 비싼 토큰일수록 한도를 많이 씁니다. 매번 새 세션을 여는 습관은 같은 작업으로 한도를 더 빨리 쓰게 만드는 셈입니다.

내가 실제로 어떤 세션에서 얼마를 썼는지는 [사용량 분석기](/ko/claude-code-usage)에 ~/.claude/projects 폴더를 넣으면 날짜·프로젝트별로 볼 수 있습니다. 하루 작업량으로 구독과 API 중 무엇이 나은지는 [코딩 에이전트 비용 계산기](/ko/agents)로 비교할 수 있습니다. 한도가 어떻게 줄어드는지는 [클로드 사용량 한도 정리](/ko/blog/claude-sayongnyang-hando)에 모아 두었습니다.

이번 측정의 요청 30개 목록, 요청별 토큰과 비용, 원본 기록은 [긴 대화 vs 새 대화 실측 데이터](/data/long-chat-vs-new-chat-cost)와 [쉬는 시간 캐시 실측 데이터](/data/ai-coffee-break-cache-cost)에서 받을 수 있습니다.

## 이번 측정의 한계

- **프로젝트 하나:** 30~40KB짜리 게임 파일 하나를 고치는 작업이었습니다. 여러 파일을 오가거나 관련 없는 작업이 섞인 긴 세션은 결과가 다를 수 있습니다.
- **같은 시간에 실행:** 세 방법(실험 2는 일곱 가지 휴식)을 같은 시간대에 함께 돌렸습니다. 그래서 공통 시스템 프롬프트 일부가 다른 세션 덕분에 캐시에 남았을 수 있습니다. 65분 휴식에서도 15,925토큰은 캐시에서 읽혔습니다. 세션 하나만 돌린다면 만료 비용이 조금 더 클 수 있습니다.
- **Opus 5.5와 Claude Code만:** 다른 모델이나 코덱스 같은 다른 도구는 캐시 방식이 달라 숫자가 달라집니다. 코덱스도 함께 돌려 봤지만 여러 개를 동시에 실행하자 파일 쓰기에서 멈춰서 결과에서 뺐습니다.
- **비용은 API 정가 환산:** 구독 요금제에서는 이 금액이 청구되지 않고, 같은 비율로 사용 한도가 줄어듭니다.

## 자주 묻는 질문

**클로드 코드에서 새 대화를 자주 열면 토큰이 절약되나요?**
같은 프로젝트를 계속 고치는 중이라면 아닙니다. 이번 측정에서 요청마다 새 세션을 연 쪽이 한 세션으로 이어 간 쪽보다 129% 더 들었습니다. 새 세션은 프로젝트를 다시 파악하면서 비싼 캐시 쓰기를 매번 했습니다.

**/compact를 쓰면 비용이 줄어드나요?**
이번 측정에서는 13% 늘었습니다. 요약 자체가 큰 요청이고, 요약 뒤에는 캐시를 다시 쌓아야 하기 때문입니다. 대화가 한도에 가깝거나 꼬였을 때 정리용으로 쓰는 편이 맞습니다.

**클로드 코드 캐시는 몇 분 동안 유지되나요?**
구독 요금제로 로그인하면 1시간입니다. 이번 측정에서도 55분까지는 캐시가 유지됐고 65분에는 만료됐습니다. API 키로 쓰거나 사용 크레딧을 쓰는 중이라면 기본 5분입니다.

**/clear와 새 세션은 다른가요?**
둘 다 대화를 비우고 새로 시작한다는 점은 같습니다. 공식 문서는 관련 없는 작업으로 넘어갈 때 /clear를 쓰라고 안내하고, 나중에 돌아올 세션이라면 /rename으로 이름을 붙여 두라고 합니다.

**점심 먹기 전에 /compact를 하면 아낄 수 있나요?**
공식 블로그는 캐시가 살아 있을 때 요약하는 편이 쉬고 나서 요약하는 것보다 싸다고 안내합니다. 요약된 대화는 원래 대화보다 작아서, 돌아온 뒤 다시 써야 할 양도 줄어듭니다. 다만 이번 측정에서는 이 경우를 직접 재지 않았습니다.

**대화가 길어지면 언젠가는 새로 여는 게 낫지 않나요?**
이번 30개 요청에서는 마지막까지 한 세션이 쌌습니다. 다만 프로젝트와 상관없는 내용이 쌓였거나, 1시간 넘게 쉬어서 캐시가 만료됐거나, 컨텍스트 한도에 가까워졌다면 새로 시작하는 편이 나을 수 있습니다.

**API 키로 클로드 코드를 쓰면 결과가 달라지나요?**
캐시 유지 시간이 기본 5분이라 쉬는 시간 실험의 결과가 크게 달라집니다. 이번에 아무 비용 변화가 없었던 6분, 15분, 30분 휴식도 API 키라면 캐시가 만료될 수 있습니다. 긴 대화와 새 대화의 차이는 요청 사이 간격이 짧다면 비슷하게 나타날 것으로 보이지만, 이번에는 구독 로그인으로만 쟀습니다.

## 마무리

같은 게임에 같은 수정 요청 30개를 보내 보니, 한 세션으로 이어 간 쪽이 가장 쌌습니다(평균 $4.16). 15번째 요청 뒤 /compact를 쓴 쪽은 13%, 요청마다 새 세션을 연 쪽은 129% 더 들었습니다. 새 세션은 입력 토큰이 오히려 적었지만, 매번 프로젝트를 다시 읽어 비싼 캐시 쓰기를 해야 했습니다.

쉬는 시간 실험에서는 55분까지 다음 메시지 비용이 똑같았고, 65분을 쉬자 캐시가 만료돼 507% 비싸졌습니다. 같은 작업은 한 세션으로 이어 가고, 새 세션은 다른 작업으로 넘어갈 때, /compact는 정리가 필요할 때 쓰는 것이 이번 측정으로 본 가장 싼 방법입니다. 프로젝트 하나, 방법별 2회 측정이라 프로젝트 크기와 요청 내용에 따라 숫자는 달라질 수 있습니다.
