# 브라우저 MCP는 토큰을 얼마나 먹을까? Playwright·Chrome DevTools 68번 실측과 직접 만든 토큰 다이어트 도구

Claude Code에 브라우저 MCP를 붙이면 토큰이 엄청나게 든다는 이야기를 자주 듣습니다. 페이지를 한 번 볼 때마다 1만~5만 토큰이 들어간다는 글도 있습니다. 정말 그런지, 그렇다면 줄일 수는 없는지 궁금해서 가장 많이 쓰이는 두 가지, Microsoft의 Playwright MCP와 Google의 Chrome DevTools MCP를 직접 재 봤습니다. 측정하다가 줄이는 도구까지 하나 만들게 되어 그 결과도 같이 정리합니다.

## 어떻게 쟀나

- Claude Code 2.1.295, 오퍼스 5.5, effort medium, Windows 11 (2026-10-22)
- 실행마다 MCP 서버를 하나만 붙이고, 웹 검색·파일 읽기·셸 같은 기본 도구는 꺼서 브라우저 도구만 쓰게 했습니다
- 서버 버전은 Playwright MCP 0.0.83, Chrome DevTools MCP 1.11.0 (둘 다 화면 없이 실행)
- 과제 7개, 일상 과제는 2회씩, 스냅샷 과제는 5회씩(전체 스냅샷만 3회), 모두 68번 실행
- 토큰은 Claude Code 로그에 남는 요청별 사용량(캐시 포함 전체 입력)으로 셌습니다

## 결과 1: 평범한 작업은 생각보다 가벼웠다

먼저 흔한 작업 4가지를 시켰습니다.

| 과제 | Playwright 입력 토큰 | 비용 | Chrome DevTools 입력 토큰 | 비용 |
|---|---:|---:|---:|---:|
| 할 일 앱에 3개 추가, 1개 완료 | 178,408 | $0.19 | 199,737 | $0.22 |
| 위키백과에서 Python 설계자와 첫 공개 연도 | 115,888 | $0.17 | 117,240 | $0.17 |
| 해커뉴스 상위 5개 글 | 90,006 | $0.16 | 93,496 | $0.17 |
| 위키백과 표에서 출시일 5개 | 91,350 | $0.16 | 93,683 | $0.16 |

(2회 평균, 비용은 오퍼스 5.5 API 가격 기준)

16번 모두 정답을 냈고, 도구가 한 번에 돌려준 결과 중 가장 큰 것도 6,012자였습니다. 오퍼스 5.5는 페이지를 통째로 읽지 않고, 필요한 부분만 뽑는 짧은 스크립트나 Playwright의 검색 도구를 썼습니다.

그러면 토큰은 어디에 갔을까요? 요청 하나에 평균 약 2만 3천 토큰이 실렸는데, 대부분은 MCP가 아니라 Claude Code 자체의 지시문과 도구 설명이었습니다. 브라우저 작업은 단계가 많아서 이 고정 비용이 단계 수만큼 반복됩니다. 할 일 앱 과제가 가장 비쌌던 것도 페이지가 커서가 아니라 클릭과 입력 단계가 많아서였습니다.

## 결과 2: 긴 페이지를 통째로 읽으면 20만 토큰

다음으로 일부러 최악의 경우를 만들었습니다. 영어 위키백과 "Python (programming language)" 문서를 열고, 페이지 전체 스냅샷(접근성 트리)을 한 번 찍게 했습니다.

- Playwright MCP: 504,168자
- Chrome DevTools MCP: 427,400자

이 글자를 그대로 오퍼스 5.5에 보내 토큰을 세어 보니 각각 **205,642토큰과 208,926토큰**이었습니다. 오퍼스 API 정가로 한 번에 약 $1.65입니다. GPT 토크나이저(o200k)로는 13만 3천~13만 8천 토큰이라, 같은 글이 Claude에서 50% 이상 더 많이 나왔습니다. 링크 주소와 요소 번호가 많은 글은 Claude 토크나이저에서 특히 불리합니다.

다행히 Claude Code는 이미 이걸 막습니다. 매번 "결과가 너무 크다"며 받지 않고 파일로 따로 저장한 뒤, 필요한 부분만 나눠 읽으라고 안내했습니다. 그래서 Claude Code에서는 20만 토큰이 한꺼번에 들어오지 않았습니다. 다만 이런 안전장치가 없는 다른 프로그램에서는 페이지 하나로 20만 토큰이 그대로 들어갈 수 있습니다. 이번에는 Claude Code만 재서, 다른 프로그램이 실제로 어떻게 하는지는 확인하지 못했습니다.

## 결과 3: 중간 크기 페이지는 그대로 들어온다

문제는 Claude Code가 막지 않는 중간 크기 페이지입니다. 해커뉴스 첫 화면 스냅샷은 그대로 들어왔고, 다음 요청을 이만큼 키웠습니다.

- Playwright MCP: 18,407토큰
- Chrome DevTools MCP: 14,115토큰

들여다보니 대부분이 쓸모없는 정보였습니다. 링크마다 붙는 주소 줄, "클릭 가능" 표시, 칸을 나누는 빈 요소, "|" 같은 구분 기호, 깊은 들여쓰기가 내용보다 많았습니다.

## 그래서 줄이는 도구를 만들었다

이름은 tokensave-mcp-diet입니다. Playwright MCP나 Chrome DevTools MCP 앞에 끼워 쓰는 작은 중간 다리이고, 동작은 세 가지입니다.

1. **압축:** 스냅샷이 크면 링크 주소, 클릭 표시, 구분 기호, 빈 요소를 빼고 들여쓰기를 줄입니다. 요소 번호는 그대로 남기 때문에 클릭과 입력은 원래대로 됩니다.
2. **개요:** 압축해도 크면 제목, 입력칸, 버튼, 링크만 남긴 개요를 보냅니다. 긴 링크 묶음(위키백과 각주 같은 것)은 몇 개만 남기고 접습니다.
3. **부분 읽기:** 원본 스냅샷은 도구 안에 보관하고, 새 도구 `snapshot_detail`로 요소 번호나 글자로 필요한 부분만 꺼내 읽게 합니다.

설치는 Claude Code의 MCP 설정에서 원래 명령 앞에 한 줄을 붙이면 됩니다. npm 계정이나 API 키는 필요 없습니다.

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["-y", "github:johnisking/tokensave-mcp-diet", "--", "npx", "-y", "@playwright/mcp@latest"]
    }
  }
}
```

같은 과제를 이 도구를 끼워서 다시 쟀습니다.

| 과제 | 서버 | 스냅샷 토큰 (그대로) | 다이어트 후 | 과제 비용 변화 |
|---|---|---:|---:|---:|
| 해커뉴스 상위 5개 | Playwright | 18,407 | 6,792 (−63%) | $0.298 → $0.205 (−31%) |
| 해커뉴스 상위 5개 | Chrome DevTools | 14,115 | 8,066 (−43%) | $0.271 → $0.224 (−18%) |
| 위키백과에서 사실 찾기 | Playwright | 5회 중 3회 거부 | 9,193 | $0.181 → $0.236 (+30%) |
| 위키백과에서 사실 찾기 | Chrome DevTools | 매번 거부 | 8,479 | $0.230 → $0.237 (+3%) |
| 위키백과 전체 스냅샷 | Playwright | 약 205,600 (Claude Code는 거부) | 9,193 (−96%) | $0.154 → $0.222 (+44%) |
| 위키백과 전체 스냅샷 | Chrome DevTools | 약 208,900 (Claude Code는 거부) | 8,479 (−96%) | $0.160 → $0.221 (+38%) |

(비용은 5회 평균, 전체 스냅샷은 3회 평균. 해커뉴스는 5회 모두 비용 차이가 1센트 안쪽이었고, 스냅샷 토큰은 실행마다 4% 안에서 같았습니다.)

해커뉴스에서는 스냅샷 토큰이 43~63%, 과제 비용이 18~31% 줄었고 5회 모두 답도 같았습니다.

위키백과는 정직하게 말해 Claude Code 안에서는 손해였습니다. Claude Code가 원래 짧은 거절 안내만 보내던 자리에 약 9천 토큰짜리 개요가 들어가서, 과제 비용이 3~44% 늘었습니다. 대신 큰 결과를 그대로 받는 프로그램이라면 20만 토큰이 9천 토큰으로 96% 줄어듭니다. 이 도구는 중간 크기 페이지를 자주 읽는 작업이나, Claude Code처럼 막아 주는 장치가 없는 환경에서 쓸모가 있습니다.

## 실제로 쓸 때 기억할 것

- Claude Code에서 브라우저 MCP 비용의 대부분은 페이지가 아니라 단계 수입니다. 단계가 적게 끝나도록 할 일을 한 번에 분명하게 말하는 게 가장 효과가 큽니다.
- 비싼 경우는 "페이지 전체를 읽어"입니다. 특정 요소, 검색, 짧은 스크립트로 필요한 부분만 달라고 하면 됩니다.
- 큰 결과를 그대로 받는 프로그램을 쓴다면 tokensave-mcp-diet 같은 중간 다리나, 스냅샷을 파일로 저장하는 서버 옵션을 켜 두는 게 안전합니다.

## 한계

- 일상 과제는 2회, 스냅샷 과제는 5회(전체 스냅샷 3회)씩, 모델 하나, 컴퓨터 하나로 잰 값입니다. 해커뉴스처럼 실시간으로 바뀌는 페이지라 점수 같은 내용은 실행마다 조금씩 달랐습니다.
- Claude Code만 쟀습니다. Claude 데스크톱 앱, Cursor, Codex가 20만 토큰짜리 결과를 그대로 받는지는 확인하지 않았습니다.
- 서버 버전이 바뀌면 스냅샷 형식도 바뀝니다. Playwright MCP는 이미 페이지 이동 때 스냅샷을 파일로 빼는 식으로 바뀌었습니다.
- 개요 모드는 본문 글을 빼기 때문에, 모델이 필요한 부분을 다시 요청해야 해서 단계가 늘 수 있습니다.

## 정리

결론부터 말하면, 브라우저 MCP가 "매번" 토큰을 크게 먹지는 않습니다. 오퍼스 5.5는 대부분 필요한 부분만 골라 읽었고, 비용의 주범은 Claude Code가 요청마다 싣는 고정 분량과 단계 수였습니다. 다만 긴 페이지를 한 번 통째로 읽으면 20만 토큰이 넘고, 중간 크기 페이지는 Claude Code에서도 그대로 들어옵니다. tokensave-mcp-diet는 그 두 경우를 줄이려고 만든 무료 도구입니다.
